# 설계

## 동기

중앙집중형 메신저는 모든 대화가 운영자의 서버에 저장됩니다. 서버를 가진 쪽이 대화 내용을 바꾸거나 지울 수 있고, 서버에 문제가 생기면 대화 내용이 사라질 수 있습니다.

그래서 대화 내용을 참여자들이 나누어 보관하도록 분산화했습니다. 하지만 분산화만으로는 누군가 자신이 가진 내용을 바꾼 뒤 "원래 이 내용이었다"고 우기는 것을 막지 못합니다. 그래서 대화 내용의 해시값과 방 활동 기록을 블록체인에 남겨, "이 시점의 대화가 이 내용이었다"는 흔적(footprint)을 누구나 확인할 수 있게 했습니다.

## 고려한 점

- **대화 내용과 증명의 분리** : 메시지 전체를 블록체인에 올리면 용량과 속도, 공개 범위가 문제가 되므로 메시지는 GunDB에 두고 SHA-256 해시값만 원장에 기록합니다.
- **서버에 비밀번호를 두지 않는 계정** : SEA는 비밀번호로 개인키를 암호화해 보관하므로, 비밀번호를 검사하는 중앙 서버가 없습니다.
- **메시지 서명** : 메시지는 보낸 사람의 키로 서명해 저장하고, 읽을 때 서명을 확인합니다.
- **방 활동 기록** : 방 개설(`create`), 입장(`enter`), 해시 기록(`record`)을 원장에 남깁니다. 기록은 덮어쓰지 않고 기록마다 새 키(`record~방~순번`)에 쌓으며, 기록 시각은 앱이 보낸 값이 아니라 트랜잭션 시각입니다.
- **해시 연결** : 해시 기록마다 덮은 메시지 수(`Count`)와 직전 해시(`PrevHash`)를 남깁니다. Check Hash는 기록마다 대화의 앞 `Count`개 메시지를 다시 해시해 비교하므로, 메시지가 추가되어도 예전 기록은 일치하고 예전 메시지가 바뀌면 그 메시지를 덮은 기록이 모두 불일치가 됩니다. 직전 해시가 최신이 아닌 기록은 체인코드가 거부합니다.
- **자동 기록** : 마지막 기록 이후 새 메시지가 10개 쌓이고 3초 동안 새 메시지가 없을 때, 그리고 새 메시지가 있는 채로 방을 나갈 때 자동으로 기록합니다. 다음 순번(`Seq`)을 함께 보내므로 여러 멤버가 같은 상태를 동시에 기록해도 하나만 남습니다.
- **회의록 내보내기** : 회의록 파일에는 메시지마다 다음 네 가지가 들어 있습니다.
  - 보낸 사람이 서명한 GUN 원본 값: 저장 위치, 필드, 암호문, 쓴 시각
  - 그 메시지만 여는 AES 키: SEA가 쓰는 SHA-256(암호화 키 + salt)
  - 평문
  - 보낸 사람의 서명된 계정 이름
  
  AES 키는 SHA-256에서 거꾸로 계산할 수 없으므로, 방 키는 드러나지 않고 다른 메시지도 열리지 않습니다. 검증 스크립트(`frontend/scripts/verify-minutes.mjs`)는 다음을 확인합니다.
  - 서명이 보낸 사람의 것인지
  - 메시지가 보낸 사람 공간에 있는지
  - AES 키로 연 평문이 파일의 평문과 같은지 (AES-GCM이라 바뀐 암호문은 열리지 않습니다)
  - 원장에 보낸 사람의 입장 기록이 있는지
  - 원장 해시가 앞 `Count`개 메시지와 일치하는지
  
  파일에서 메시지를 빼거나 끼워 넣으면 원장 해시와 어긋납니다.
- **초대** : 초대는 방 기록과 다른 키(`invite~받는사람 공개키~방`)에 저장해 방의 최신 해시를 덮어쓰지 않고, 받은 사람이 수락하거나 거절할 때까지 남습니다. 보내기는 보낸 사람의 서명이, 조회와 응답은 받는 사람의 서명이 있어야 하며, 보낸 사람의 서명은 초대에 함께 저장됩니다 (#35).
- **암호화 방** : 방을 만들 때 자유 방과 암호화 방 중에 고릅니다. 암호화 방의 메시지는 방 비밀번호로 만든 방 키로 암호화합니다. 초대에는 방 키를 받는 사람만 열 수 있게 암호화해 담으므로, 초대를 수락하면 비밀번호 없이 들어갑니다. 한 번 들어간 방의 키는 각자의 사용자 공간에 암호화해 보관합니다.
- **React Native에서의 암호 연산** : React Native에는 SEA가 필요로 하는 WebCrypto가 없어서, 보이지 않는 WebView 안에서 암호 연산을 수행하도록 연결했습니다(`frontend/lib/cryptoBridge.js`).
- **P2P 방식의 문제** : 사용자 간 동기화(메시지 순서 정렬) 지연, 각 기기의 로컬 저장 공간 낭비, 회의록·대화 내용 보관 같은 부가 기능의 부재를 함께 고려했습니다.

## 한계와 개선 방향

- 자유 방의 메시지 암호화에 쓰는 키는 방 안에 공개되어 있어, 방 이름을 아는 사람은 내용을 읽을 수 있습니다. 비밀 대화는 암호화 방을 사용합니다.
- 암호화 방의 비밀번호 확인값은 공개되어 있어, 짧은 비밀번호는 오프라인 대입 공격에 약합니다.
- 해시는 앱이 계산해 보냅니다. 기록 직전에 보냈지만 기록한 사람에게 늦게 동기화된 메시지는 기록의 앞 `Count`개 안으로 들어가 변조로 보일 수 있습니다.
- 원장 기록 요청은 앱이 사용자 키로 서명하고 API 서버가 확인하며, 서명은 기록에 함께 저장됩니다 (#20). 다만 트랜잭션은 모두 하나의 Fabric 계정으로 제출되어 체인코드가 서명을 직접 확인하지는 않고, 계정 이름(`HostID`, `PostID`)은 서명한 공개키와 대조하지 않습니다.
- 회의록의 서명은 메시지를 쓴 계정(공개키)과 그 키가 서명한 계정 이름까지만 증명합니다. 그 계정을 실제로 누가 쓰는지는 연결하지 않습니다. 기관이 확인한 명부를 원장에 두는 방법을 [docs/ideas.md](ideas.md)에 적어 두었습니다.
- 휴대폰에는 파일 저장 모듈이 없어서, 회의록을 공유 창의 텍스트로 넘깁니다. 받은 사람이 `.json` 파일로 저장해야 합니다.
- Relay와 API 서버가 각각 한 대이며, Fabric은 테스트 네트워크에서만 확인했습니다.
