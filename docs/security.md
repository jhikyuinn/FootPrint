# 보안 설계와 공격 실험

이 문서는 확인한 것만 적습니다. 테스트로 확인한 항목에는 테스트를, 코드로만 확인한 항목에는 그렇게 표시합니다.

## 공격자 가정

- 같은 GUN relay에 접속할 수 있는 누구나: 로그인하지 않고도 relay에 직접 읽고 쓸 수 있습니다.
- API 서버를 호출할 수 있는 누구나: API 서버는 요청의 사용자 서명을 확인합니다 (#20, #35).
- 지킬 것: 메시지 내용, 누가 썼는지, 방 멤버와 방 목록, 원장 기록과 대화의 일치.

## 1. 막도록 설계하고, 공격해서 막히는 것을 확인한 것

`npm run e2e:attacks` (`frontend/e2e/attacks.mjs`). 공격자는 로그인하지 않은, SEA 없는 순수 GUN 클라이언트이고, 다른 사용자의 방 목록(`~공개키/entered`)을 relay에 직접 써서 공격합니다.

| 공격 | 막는 방법 | 결과 |
|---|---|---|
| 서명 없이 다른 사람 공간에 방을 넣거나 지우기 | 사용자 공간의 값은 그 사용자 키로 서명돼야 함 (SEA) | relay가 `Unverified data.`로 거부, 목록 그대로 |
| 그 사용자가 다른 키에 서명한 값을 다른 키로 옮겨 쓰기 | 서명이 노드 이름, 키, 값, 시각을 함께 묶음 (`gun/sea.js`의 `SEA.opt.pack`) | 거부 |
| 나간 방의 예전 서명 값(`true`)을 다시 보내 되살리기 | 서명에 시각이 들어 있어, 새 시각으로 다시 보내면 서명이 맞지 않음 | 거부, 나간 방이 되살아나지 않음 |
| 위 공격 뒤 새 기기에서 로그인 | relay도 서명을 검사해 저장하지 않음 | 방 목록 그대로 |

알게 된 것:

- relay(`backend/gun-relay/server.js`)에는 SEA를 불러오는 코드가 없지만, Node의 `require('gun')`이 `gun/lib/server.js`에서 SEA를 함께 불러와 relay도 서명을 검사합니다. 다만 `try{require('../sea');}catch(e){}`라서 불러오기에 실패하면 오류 없이 검사 없이 동작합니다. 이 테스트가 그런 변화를 드러내는 역할을 합니다.
- 사용자 공간에서는 하위 노드로 가는 연결(`entered`)도 서명된 값이라, SEA 없는 클라이언트는 그 연결을 따라가지 못하고 하위 노드 이름(`~공개키/entered`)으로 직접 접근해야 합니다. 테스트는 공격자가 대상 값을 실제로 읽었는지 먼저 확인하고(`(setup)` 항목), 그다음 공격합니다. 이 확인이 없던 첫 실행은 공격이 닿지 않은 채 모두 통과했습니다.

## 2. 뚫리는 것을 확인하고 고친 것

### 방 목록을 다른 사람이 바꿀 수 있음 (#85)

- **문제:** 들어간 방 목록이 누구나 쓸 수 있는 공용 노드 `footprint/entered/<아이디>`에 있었습니다. GUN은 같은 아이디의 여러 계정을 막지 않아, 그 계정들이 목록도 같이 썼습니다.
- **고친 방법:** 목록을 사용자 공간 `gun.user().get('entered')`로 옮겼습니다. 예전 목록은 로그인 뒤 계정마다 한 번 옮기고, 그 뒤로는 읽지 않습니다. 이미 새 목록에 있는 방(나간 방의 `null` 포함)은 옮기지 않아, 나간 방이 예전 목록에서 되살아나지 않습니다.
- **확인:** `npm run e2e:rooms`의 공격 항목 "a room someone else put in the old list does not show"(로그인하지 않은 다른 클라이언트가 예전 공용 목록에 방을 넣고 다른 방을 지움)를 같은 relay와 같은 절차로 실행했습니다.

| 코드 | 결과 |
|---|---|
| 고치기 전 (`master`, d9e02a9) | FAIL: 공격이 내 방 목록을 바꿈 |
| 고친 뒤 (38982e4) | PASS |

## 3. 설계로 막은 것 (공격 테스트는 없음)

| 위협 | 막는 방법 | 확인 |
|---|---|---|
| 다른 사람 프로필 사진에 외부 URL을 넣어, 보는 사람 기기가 그 서버에 접속하게 함 (IP 노출) | JPEG/PNG data URI이고 10만 자 이하일 때만 사진으로 씀 (`frontend/lib/profileData.js`) | 단위 테스트 `lib/profileData.test.mjs` |
| 표시 이름으로 다른 사람 사칭 | 표시 이름을 두지 않고, 채팅에는 서명된 계정 아이디만 보여 줌 (#12) | 설계 |
| GUN 멤버 목록에서 다른 멤버를 지워 숨김 | 화면의 멤버는 GUN 목록에 있거나 원장에 `leave`가 없는 사람. 원장 기록은 지울 수 없음 (#41) | 정상 나가기만 `e2e:leave`로 확인, 남이 지우는 경우는 테스트 없음 |

## 4. 알려진 한계 (대응하지 않음)

- **방 비밀번호 오프라인 대입:** 암호화 방 정보의 `salt`와 `check`(비밀번호로 만든 키로 암호화한 고정 문자열)가 공개돼 있어, 서버 없이 비밀번호를 대입해 볼 수 있습니다. 방 비밀번호는 8자 이상이어야 하고(#33) 키는 `SEA.work`(PBKDF2)로 만들지만, 결국 비밀번호 강도에 달려 있습니다.
- **나간 멤버와 방 키:** 방 키가 방 비밀번호에서 만들어지므로, 나간 사람은 비밀번호로 키를 다시 만들 수 있습니다. 막는 방법은 `docs/ideas.md`의 "나간 멤버가 암호화 방의 새 메시지를 못 읽게 하기"에 있습니다.
- **예전 방 목록을 옮길 때:** 공용 목록에 이미 누군가 넣어 둔 방은 처음 옮길 때 함께 옮겨집니다. 어느 계정이 넣었는지 구분할 수 없습니다.
- **공개되는 정보:** 메시지 내용은 암호화되지만 방 이름, 멤버 공개키, 메시지 시각은 누구나 볼 수 있습니다.
- **API 서버:** 모든 원장 기록이 API 서버의 Fabric 계정 하나(User1)로 들어갑니다. API 서버가 장악되면 원장에 무엇이든 쓸 수 있습니다.
- **전송 구간:** HTTPS / WSS는 아직 적용하지 않았습니다 (#25).
- **요청 횟수 제한:** API 서버에 요청 횟수 제한이 있는지는 확인하지 않았습니다.
