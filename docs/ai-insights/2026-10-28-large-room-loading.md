# 메시지가 많은 방이 느린 원인: 전체 다시 그리기 (#45)

- 지적/발견: 5,000개 방에서 최근 메시지가 43~46초 뒤에 보였다. 단계별로 재 보니 복호화(1,000개에 0.2초)와 목록 정렬(0.4초)은 원인이 아니었다. 메시지가 올 때마다 화면 전체를 다시 그리는 것이 원인이었다(React 렌더 합계 1,000개 0.9초 → 5,000개 8.5~11.9초, 약 O(n^1.5)). 그리는 동안 메시지 받기도 같이 밀렸다.
- 판단: 반영함. 화면에는 최근 50개만 그리고, 위로 스크롤하면 50개씩 더 그린다. 해시는 지금처럼 받은 메시지 전체로 계산한다.
- 이유: 50개만 그리는 실험에서 같은 방이 19~21초로 줄었다. 받기 자체를 줄이는 방법(최근 키만 받기)은 해시 때문에 결국 전부 받아야 해서 따로 조사가 필요했다.

## 측정 (`npm run e2e:load`, PC Chrome, 개발 서버, 5,000개 방)

| | 최근 메시지 보임 | 위로 스크롤 후 이전 50개 |
|---|---|---|
| 바꾸기 전 | 43~46초 (2회) | 이미 전부 그려져 있음 |
| 바꾼 뒤 | 17.4~19.4초 (6회) | 0.2~0.6초 (도착이 끝난 뒤) |
| 바꾼 뒤, 프로덕션 웹 빌드 | 15.3~17.2초 (2회) | 0.3초 |

구현 중 발견한 것:

- 웹 브라우저의 스크롤 고정(`overflow-anchor`)이 그리는 메시지가 바뀔 때 스크롤 위치를 옮겼고, 앱은 이것을 "사용자가 위로 올림"으로 보고 그리는 범위를 계속 넓혔다(5,000개 중 4,964개를 그림). 웹에서 이 기능을 끄고, 위치가 실제로 위로 움직였을 때만 "위로 올려 읽는 중"으로 본다.
- 남은 시간 중 약 3초는 메시지 수와 상관없이 방을 열 때 `readOnce`를 1초씩 세 번 차례로 기다리는 시간이다. 반영하지 않고 `docs/ideas.md`에 적었다(#45 완료 기준 밖).

폰과 iOS에서는 측정하지 않았다.
